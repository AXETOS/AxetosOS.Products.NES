# AxetosOS.Products.NES v2.20.1

## Exact PPUSTATUS provenance hotfix

The v2.20.0 Alien Syndrome trace exposes a strong causal correlation between the previous frame's sprite-zero latch and the title-phase MMC1 raster family. When the preceding visible frame records a sprite-zero hit, the game performs about 131-132 mirrored PPUSTATUS reads and the final poll occurs at pre-render scanline 261 before the first CHR1 commit appears around scanline 30. When the preceding frame has no sprite-zero hit, the poll path performs only two reads and the same MMC1 sequence begins around scanline 20 or 24. The two CHR1 commits still remain exactly 8,692 CPU cycles apart.

v2.20.0's CPU-side observer correctly identified the polling address and caller (`PC=$81C1`, opcode `$AD`) but could not sample the compiled data bus at the completed-read phase, so status bytes were printed as `v=??`.

### What v2.20.1 changes

`DesktopHost` now enables the RP2C02's existing external `SplitTraceOutput` whenever cartridge-video provenance tracing is active and dispatches each captured split event to both consumers: the cartridge provenance collector and, when explicitly requested, the existing `--ppu-split-trace` console output. No consumer steals events from the other.

`CartridgeVideoTraceCollector` consumes only `PPUSTATUS read` split events. Those events already contain the exact byte generated by RP2C02 before the read side effect clears vblank, so each MMC1 mapping commit now reports:

- CPU-side PPUSTATUS poll count separately as `ppustatus-bus-from-nmi`;
- exact PPU status counts as total / sprite-zero-clear / sprite-zero-set;
- exact vblank-clear / vblank-set status counts;
- whether sprite zero was latched at the most recent NMI;
- exact last PPUSTATUS value and raster;
- exact last sprite-zero-clear and first sprite-zero-set observations;
- the existing CPU-side `$81C1` provenance as a separate field.

### Architectural boundary

This is diagnostic-only. RP2A03, RP2C02, MMC1, motherboard and compiler execution behavior is unchanged. No chip gains peer knowledge, callbacks or execution feedback. DesktopHost only captures and drains an already-existing package-owned diagnostic output.

Validation target: **266 tests**. User-local `dotnet test` remains the acceptance gate.
